# Release history

Newest first. Downloads are on the [Releases](https://github.com/mattpetosa/empower-smart-project-backup-releases/releases) page.

## v3.10.0.1-0.1.2 (2026-10-30)

### Changed
- **Report Bugs, bottom right.** The author credit in the footer is replaced by a **Report Bugs** button with a bug icon. It opens the bug form of Smart Tools Feedback on GitHub — the one place to report a problem with any Smart Tools app — with the title already tagged **[Smart Project Backup]** and the "Which app?" line filled in with Smart Project Backup and the exact version you're running. Nothing else is sent: it is a public page, so no paths, server or database names, or anything from your logs go into it. Describe what happened, what you expected and how to repeat it, and submit.
- **A license key for another app says which one, with its current name.** Entering a key that belongs to a different Smart Tools app still refuses it and names the app it is for; a Project Mover/ESPM- key is now named Empower Smart Project Migration, the tool's new name.

## v3.10.0.1-0.1.1 (2026-10-28)

### Added
- **The Empower Smart Project Backup window,** in the Empower Smart Tools look (blue). Activate and license details sit at the top, as in the other Smart Tools; each action opens as a checklist you review before pressing Start, with each step's progress and log shown as it runs.
- **Scheduled backups run without a window,** started by Windows Task Scheduler as the Windows account you choose for the job. If a scheduled run can't start or stops on an unexpected error, it leaves a log saying why in C:\Client\Settings\Empower Smart Project Backup\State\Logs (passwords are never written to it).
- **Opens as administrator.** Opened without administrator rights, it asks for them (the usual Windows prompt) and opens again.
- **Closing the window while a run is going asks first.** Closing stops that run part-way, and a backup that didn't finish is not kept as a good backup. Scheduled backups are not affected.
- **Updates itself,** like the other Empower Smart Tools: it looks for a new version when it opens, and the update button installs it. Updates never need a license, and your jobs, schedules and backup history stay as they are.
- **Licensed like the other Empower Smart Tools.** Activate with the license key emailed to your @waters.com address. Creating or editing backup jobs and running backups need an active license; Check System, the backup health view, restoring a project from its backups, and updates work without one.
- **A scheduled backup never fails silently on an inactive license.** If the license is not active (not activated, expired, or activated on another computer), the scheduled run backs nothing up and sends a failure alert saying why.
- **License keys start with ESPB-.** They use only capital letters and digits, in groups of five; when you enter one, case, spaces, line breaks and dashes don't matter. A key for another Smart Tools app is refused with a message naming the app it is for, and a key with a mistyped character says so.
- **Using Empower's built-in System account for the backups asks twice.** It works, but people sign in as System, its password would be kept on the server, and a password change or lockout stops the backups; setup explains this and recommends a dedicated account, and Check System keeps a reminder.
- **Setting up a job asks for the Empower backup account once,** right at the start. That sign-in tests the account, and the projects you choose from are the ones it can see, so a job never holds a project its backups can't reach. The project list has Select all and Clear all.
- **Setup gives the Windows account Modify on a backup folder on this computer,** so old backups made with Run now can be removed too, and it tests that the account can delete files it didn't make (on a network share, ask its administrator for Modify).
- **Setup gives the Windows account the "Log on as a batch job" right** that scheduled tasks need, and puts it back each time the app opens.
- **Setup checks the Windows account before saving anything:** its password, that no policy denies it "Log on as a batch job" (including domain policy), that it can write, read and delete in the backup folder, and that it may start the program itself (so keep Empower Smart Project Backup in a folder every account can read, for example under C:\Program Files, not in your own Desktop or Downloads).
- **Scheduled backups run as your named Windows account; Windows keeps its password.** Empower Smart Project Backup never stores or displays it. Each time the app opens, it makes sure every job's account can still read what it needs; Check System shows it if that fails.
- **A project in use is left for the next run.** A project that is fully locked in Empower, or whose raw data was written in the last 15 minutes (for example during an acquisition), is not backed up that night. The summary and email count it as "in use", not as failed, and it still sends the failure alert, because that project has no new backup.
- **Email alerts use your own mail server** on port 587 (STARTTLS) or an internal relay on port 25; port 465 isn't supported.
- **The health view shows when a job's scheduled task didn't run, and why** (for example a changed password).
- **A backup that didn't start is reported, even with only one job.** When a job's Windows account can't log on (its password changed or expired, the account was disabled), Windows never starts the backup and keeps showing the last run as fine. An hourly missed-run check, which runs as the computer's own SYSTEM account and needs no password, now notices: it emails the job's recipients (when the job has email) and writes a warning to the Windows Application event log, once for each missed run. It is set up and removed with the jobs; Check System and Backup health show it. Because it runs as SYSTEM, it is only set up from a copy of the app that only administrators can change, such as one under C:\Program Files.
- **Back up only what changed.** Before each backup, every project is checked: its audit trail, what it holds in the database (sample sets, injections, results and methods), its size in Empower and its raw data folder. A project where nothing changed since its last good backup is left as it is, and that backup stays current, so on a large job a quiet night takes minutes instead of hours. Any doubt (something that can't be read, or no earlier backup to compare with) means the project is backed up. It is on for new and existing jobs and can be switched off per job, to back up every project on every run as before.
- **Unchanged projects are still backed up again regularly,** every 7 days by default, up to 100 GB of them a night (both can be changed per job). Changed projects are always backed up that night, whatever their size. On a large job this becomes a rotation, and the health view shows how often every unchanged project gets a new backup, with a warning if that is more than 30 days.
- **A nightly stop time (optional):** after it, a scheduled run starts no new project. The one in progress finishes, and the rest go first at the next run. A project that hasn't had its turn for 3 runs in a row is shown as a warning (in the health view, and by email then and every 7 runs while it still waits), with what to change. The first backup of a large job spreads over several nights this way, and the health view says how many projects are still waiting for one. If Windows starts a scheduled run late, after its stop time (for example because the computer was off), that run still backs up the projects that changed (every project, for a job that backs up everything) and leaves only the regular re-backups for the next night.
- **Run now asks once:** back up only what changed (recommended), or back up everything now. Run now ignores the nightly limit and stop time.
- **History, health and email say what happened to each project:** backed up, unchanged since its last backup, deferred to the next run, or failed, with the reason in plain words (for example "the audit trail grew from 1,204 to 1,233 entries"). Unchanged and deferred projects are never counted as failures and never trigger a missed-run alert.
- **Projects without Full Audit Trail are covered too.** Many projects keep no project audit trail (Full Audit Trail is off, or the trail came back empty after a copy or restore). For them, what the project holds in the database, its size and its raw data decide: a new acquisition, processing, deletion or a method saved again means it is backed up. Changes these can't see (for example editing a field of an existing sample without processing it again) are picked up by the regular re-backup.
- **The backup's own entries in a project's audit trail don't count as changes.** Entries Empower adds for the backup itself, such as its record of the backup, are told apart by who made them: only entries made by the backup account are ignored, and a single entry by anyone else means the project changed and is backed up. Use an Empower account for backups that nobody works as.
- **The Empower backup account should be able to read project audit trails.** When it can't, setting up the job warns you, and every project is backed up on every run.
